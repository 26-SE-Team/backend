# StayView 백엔드 구현 보고서

## 1. 구현 기준

- API 기준: `API명세서.txt`
- DB 기준: `데베.txt`
- 수업/PPT 반영 기준: `피피티 내용.txt`

이번 구현은 프론트 연결보다 발표용 구조 설명이 중요하다는 요구를 반영해서, 단순 기능 나열보다 코드 구조가 수업 키워드와 직접 연결되도록 구성했습니다.

## 2. PPT 내용 반영 위치

| PPT 핵심 내용 | 구현 위치 | 반영 방식 |
| --- | --- | --- |
| Client-Server Architecture | `src/main/java/com/stayview/backend/domain/*/controller` | React Client가 HTTP API를 호출하고, Spring Server가 DB 처리를 담당하는 구조로 API 경계를 분리 |
| Layered Architecture | `controller -> service -> repository -> entity` 패키지 구조 | Controller는 요청/응답만 담당하고, Service는 비즈니스 규칙, Repository는 DB 접근만 담당 |
| MVC | `*Controller`, `*Response`, `*Request`, `*Entity` | Controller와 Model(Entity/DTO)을 분리하고, View 역할은 프론트가 담당하는 형태로 설계 |
| Encapsulation / 낮은 결합도 | `domain/*/dto` | Entity를 API 응답으로 직접 반환하지 않고 DTO로 감싸 내부 DB 구조 노출을 줄임 |
| Repository Pattern | `domain/*/repository/*Repository.java` | Spring Data JPA Repository로 DB 접근 책임을 별도 계층에 캡슐화 |
| DTO Pattern | `UserResponse`, `SpaceResponse`, `AgentProfileResponse`, `ChatRoomDetailResponse` 등 | Request/Response DTO를 만들어 API 스펙과 내부 엔티티 변경을 분리 |
| Error Handling | `common/error/GlobalExceptionHandler.java` | 예외를 한 곳에서 처리해 Controller 중복 코드를 제거하고 일관된 API 오류 응답 제공 |
| Coding Standard | 전체 Java 패키지 | CamelCase, `Request`/`Response` 접미사, domain별 패키지, RESTful 경로를 통일 |
| Javadoc / 주석 | 각 Controller 메서드 | API 목적과 구현 의도를 발표에서 바로 설명할 수 있도록 메서드 단위 주석 추가 |
| Refactoring | 기존 단일 `BackendApplication` 골격에서 domain 구조로 확장 | Controller 안에 DB 로직을 넣지 않고 Service/Repository로 역할 분리 |
| Static Analysis / Inspection | `./gradlew test` | 기본 컨텍스트 로딩 테스트로 JPA 매핑과 Spring Bean 구성을 검증 |

## 4. DB 명세 수정 사항

원본 DB 명세는 MySQL 문법이었고 Supabase는 PostgreSQL이므로 아래 내용을 수정했습니다.

| 원본 | 수정 | 이유 |
| --- | --- | --- |
| 백틱 사용, `DATETIME`, `ENUM`, `JSON` | PostgreSQL 문법, `TIMESTAMPTZ`, `VARCHAR + CHECK`, `JSONB` | Supabase PostgreSQL 호환 |
| `user` 테이블명 | `users` | PostgreSQL 예약어/시스템 객체와 충돌 가능성 회피 |
| 단수 테이블명 일부 | `agent_profiles`, `spaces`, `space_images`, `chat_rooms`, `chat_messages`, `favorites` 등 복수형 | JPA Entity와 API 도메인 명명 규칙 통일 |
| BIGINT 수동 ID | `GENERATED BY DEFAULT AS IDENTITY` | API에서 공간/사용자/채팅 메시지를 생성하려면 자동 증가가 필요 |
| 회원탈퇴 처리 컬럼 없음 | `users.is_deleted`, `users.deleted_at` 추가 | `/api/users/me/delete` 구현 시 FK 보존을 위해 소프트 삭제 적용 |
| 찜 중복 제약 없음 | `favorites(user_id, space_id)` UNIQUE 추가 | 같은 사용자가 같은 공간을 중복 찜하지 않도록 보장 |
| 채팅방 중복 제약 없음 | `chat_rooms(space_id, tenant_id)` UNIQUE 추가 | 같은 공간-사용자 조합의 채팅방 중복 방지 |
| 검색 인덱스 없음 | `spaces.status`, `room_type`, `deposit`, `monthly_rent` 인덱스 추가 | 공간 목록/검색 API 성능 고려 |
| 일부 `updated_at` 없음 | `chat_rooms`, `favorites`, `three_d_models`에 `updated_at` 추가 | 공통 감사 필드(`BaseTimeEntity`)와 유지보수성 반영 |

적용 SQL은 `src/main/resources/db/schema.sql`, 발표/시연용 샘플 데이터는 `src/main/resources/db/seed.sql`에 있습니다.

## 5. 인증 구현 범위

Google/Kakao OAuth는 실제 프론트와 OAuth Client Secret이 없어서 외부 로그인 연동 대신 데모 로그인으로 구현했습니다.

- `GET /api/auth/google`
- `GET /api/auth/kakao`

두 API는 이메일/이름 파라미터로 사용자를 생성 또는 조회하고, 이후 보호 API는 `X-User-Id` 헤더를 사용합니다. 발표에서는 "OAuth 연동 지점은 Controller/Service로 분리해두었고, 실제 Provider 연동은 AuthService 내부 구현만 교체하면 된다"고 설명하면 됩니다.

## 6. Supabase 반영 상태

DB 반영 대상 파일:

- `src/main/resources/db/schema.sql`
- `src/main/resources/db/seed.sql`

실행 명령:

```bash
psql "$SUPABASE_DATABASE_URL" -f src/main/resources/db/schema.sql
psql "$SUPABASE_DATABASE_URL" -f src/main/resources/db/seed.sql
```

Supabase Direct connection은 현재 환경의 IPv4 네트워크에서 접근할 수 없어, Supabase Shared Pooler(Session pooler) 연결 문자열로 적용했습니다.

```text
host=aws-1-ap-northeast-2.pooler.supabase.com
port=5432
database=postgres
user=postgres.ipethrelndzbgvmcstvr
```

적용 결과:

- 테이블 11개 생성 완료
- 데모 사용자 3명 생성
- 승인된 중개사 1명 생성
- 데모 공간 1개, 이미지 2개, 찜 1개, 채팅방 1개, 채팅 메시지 2개 생성
